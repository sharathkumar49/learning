

Data Engineering Pipeline Overview:
Below is a structured breakdown of the four core stages in a data engineering workflow on Google Cloud Platform (GCP). Each section covers the objectives, key concepts and all GCP products mentioned in the discussion.



Pipeline Flow:
Ingestion → Storage → Processing & Analysis → Exploration & Visualization



1. Data Ingestion:
Purpose:  
Gather raw data from various sources and bring it into GCP.

Key concepts  
- Sources: application event logs, clickstream data, eCommerce transaction records  
- Modes:
  - Streaming ingest for real-time data  
  - Batch ingest for periodic data transfers  

GCP products  
- Streaming  
  - Cloud Pub/Sub  
- Batch  
  - Storage Transfer Service (import from on-prem or other clouds)  
  - gsutil (command-line utility for Cloud Storage uploads)  

Typical flow  
1. Identify source and data format  
2. Choose streaming vs. batch  
3. Use Pub/Sub or Storage Transfer/gsutil to land data in GCP



2. Data Storage:
Purpose:
Persist ingested data in cost-effective, durable stores tailored to its structure and access patterns.

Categories & GCP products

| Data Type                   | Usage               | GCP Service(s)           |
|-----------------------------|---------------------|--------------------------|
| Structured – transactional  | OLTP databases      | Cloud SQL, Cloud Spanner |
| Structured – analytical     | Data warehouse      | BigQuery                 |
| Semi-structured / streaming | Indexed lookups     | Datastore, Bigtable      |
| Unstructured                | Object/blob store   | Cloud Storage            |
| Log data                    | Audit & diagnostics | Cloud Logging            |

Notes  
- BigQuery doubles as both storage and analytical processing engine.  
- Cloud Spanner supports global transactions at scale.  
- Datastore offers rich query language; Bigtable provides wide-column storage.  



3. Data Processing & Analysis:
Purpose:  
Transform raw or stored data into meaningful insights through ETL, analytics and machine learning.

Sub-stages & tools

- ETL & Batch/Stream Processing  
  - Dataproc (managed Hadoop/Spark clusters)  
  - Dataflow (fully managed Apache Beam pipelines)  
  - Dataprep (interactive data cleansing & preparation)  

- Analytics & Query  
  - BigQuery (standard SQL analytics)  
  - BigQuery ML (build and run ML models directly in BigQuery)  

- Machine Learning & AI  
  - Dataproc Spark ML (custom Spark ML pipelines)  
  - Vertex AI  
    - AutoML for automated model building  
    - Custom training & deployment  

Choosing a path  
1. Define desired outcome (report, prediction, anomaly detection)  
2. Select ETL/processing tool based on scale and latency needs  
3. Leverage BigQuery for standard analytics or Vertex AI for advanced ML  



4. Data Exploration & Visualization:
Purpose:  
Present processed insights to stakeholders and enable ad hoc exploration.

GCP tools

- Google Data Studio  
  - Drag-and-drop dashboard builder  
  - Connectors to BigQuery, Cloud SQL, etc.  

- BI Engine  
  - In-memory acceleration for Data Studio and other BI tools  

- Datalab  
  - Jupyter notebook environment  
  - Preinstalled data science libraries for programmatic viz  

- Vertex AI Prebuilt APIs  
  - Speech, Vision, Language APIs for specialized inferral (e.g., sentiment analysis)  

Typical workflow  
1. Connect Data Studio or Datalab to your processed data store  
2. Build dashboards or notebooks for visualization  
3. Optionally call Vertex AI APIs for domain-specific tasks  



Bringing It All Together

In this course, you will:
1. Explore each pipeline stage in depth  
2. Learn how to combine GCP products into end-to-end data pipelines  
3. Hands-on practice with ingestion, storage, processing and visualization

Types of Data:
Below is a structured overview of the three data types—structured, semi-structured and unstructured—covering their key characteristics, examples and GCP storage options.



Summary Comparison

| Data Type         | Schema                   | Access Model              | GCP Storage Services                          | Typical Examples                       
|-------------------|--------------------------|---------------------------|-----------------------------------------------|----------------------------------------|
| Structured        | Fixed, tabular schema    | SQL (rows & columns)      | Cloud SQL, Cloud Spanner                      | Relational tables: orders, customers   |
| Semi-structured   | Flexible, property-based | Key-value or document API | Cloud Datastore, Cloud Bigtable, Memorystore  | JSON documents, XML, graph records     |
| Unstructured      | No predefined schema     | Object or file system API | Cloud Storage, Filestore                      | Images, video, audio, log files        |



1. Structured Data

Structured data is organized into tables of rows and columns with a fixed schema defined up front. Each row follows the same column definitions; you interact using SQL.

Key Characteristics  
- Fixed schema: columns and data types defined before ingestion  
- Uniform rows: every record has the same fields  
- Relational model: tables can be joined via keys  

Common Systems  
- MySQL, PostgreSQL, Oracle, SQL Server  

GCP Options  
- Cloud SQL for managed MySQL/PostgreSQL/SQL Server  
- Cloud Spanner for horizontally scalable, globally distributed relational data  


# Example: Book & Author Tables

Book Table:
  
| Book ID | Book Name            | Author ID |
|---------|----------------------|-----------|
|     100 | C Programming        |         1 |
|     101 | Java Fundamentals    |         2 |
|     102 | Python Cookbook      |         1 |

Author Table:
  
| Author ID | Author Name     |
|---------:|-----------------|
|        1 | Alice Smith     |
|        2 | Bob Johnson     |

Relationship: 'Book.AuthorID = Author.AuthorID' enforces referential integrity and enables joins across tables.




2. Semi-structured Data

Semi-structured data mixes structure with flexibility: records share some common fields, but each can have a different set of properties. JSON is the most common representation.

Key Characteristics  
- No fixed schema; properties can vary per record  
- Stored as key-value pairs or documents  
- Queryable via document-oriented or key-value APIs  

Common Systems  
- MongoDB, Cassandra, Neo4j  

GCP Options  
- Cloud Datastore (Firestore in Datastore mode) for document storage with rich queries  
- Cloud Bigtable for high-throughput wide-column storage  
- Memorystore for in-memory key-value caching  

# Example: Student Documents

'''json
// Document 1
{
  "studentID": "S001",
  "name": "Emma",
  "score": 92,
  "country": "India"
}

// Document 2
{
  "studentID": "S002",
  "name": "Liam",
  "rank": 5
}
'''

Documents share 'studentID' and 'name' but differ in other properties ('score', 'country', 'rank'), illustrating schema flexibility.





3. Unstructured Data

Unstructured data has no inherent schema or predictable structure. It includes any binary or free-form content.

Key Characteristics  
- No predefined model or schema  
- Accessed via blob or file-system APIs  
- Requires specialized processing (e.g., image/video analysis, text mining)  

Common Examples  
- Images, videos, audio recordings, logs, PDFs  

GCP Options  
- Cloud Storage for object-based, unlimited-scale blob storage  
- Filestore for managed NFS volumes when POSIX file semantics are needed  



*With these definitions and examples in your notes, you now have a clear roadmap for choosing the right storage technology on GCP based on your data’s structure.*

Batch Data vs Streaming Data Processing:
Understanding the differences between batch and streaming data processing is crucial for designing efficient data pipelines. Below is a detailed comparison, complete with definitions, characteristics, examples, and a timeline diagram.



Batch Data Processing:

Batch data processing handles large volumes of data in discrete chunks at scheduled intervals.

- Defined window  
  Data arrives in a known start-to-end period.  

- Predictable size  
  You know the data volume before processing.(we have a defined start and end of the data)  

- Periodic execution  
  Jobs run at fixed intervals (e.g., hourly, daily).  

- Higher latency  
  Processing can take minutes, hours, or longer due to volume.  

- Typical example  
  End-of-day payment settlement, weekly invoices, or payroll runs.  

  
Timeline Diagram (ASCII)  

'''
Time →
┌────────┐    ┌────────┐    ┌────────┐
│ Batch1 │    │ Batch2 │    │ Batch3 │
└────────┘    └────────┘    └────────┘
    ↑             ↑             ↑
 Scheduled     Scheduled     Scheduled
  at T0          at T1          at T2
'''




Streaming Data Processing:

Streaming data processing ingests and processes records continuously as they arrive, with no predefined end.

- Unbounded flow  
  Data stream has no fixed start or end.  

- Unknown size  
  Volume grows indefinitely; you never wait to accumulate a complete set.  

- Continuous processing  
  Each record is handled in real time or micro-batches.  

- Low latency  
  Processing occurs within milliseconds to seconds.  

- Typical example  
  Stock ticker analysis, real-time fraud detection, sensor telemetry.  

  
Timeline Diagram (ASCII)  

'''
Time →
|→ r1 → r2 → r3 → r4 → r5 → r6 → … 
 Continuous real-time processing
'''



Key Differences at a Glance:

| Aspect              | Batch Processing             | Streaming Processing        |
|---------------------|------------------------------|-----------------------------|
| Data window         | Bounded (start/end known)    | Unbounded (continuous)      |
| Latency             | High (minutes to hours)      | Low (ms to seconds)         |
| Volume knowledge    | Pre-known before run         | Unknown, grows over time    |
| Scheduling          | Fixed intervals              | Always on, event-driven     |
| Use cases           | Billing runs, ETL jobs       | Live analytics, monitoring  |



*With this comparison in your notes, you can choose the appropriate processing model based on data arrival patterns, latency requirements and system design goals.*

GCP Global Infrastructure: Regions & Zones
A well-architected application on Google Cloud relies on understanding the geographic hierarchy—Global → Multi-Region → Region → Zone—and how it underpins performance, availability, disaster recovery, and compliance.



1. Hierarchy of Deployment Units

1. Global  
   Represents Google Cloud’s entire network fabric across the world.

2. Multi-Region  
   A grouping of two or more geographically proximate regions that act as a logical collective (e.g., “asia” might span Singapore + Taiwan).  

3. Region  
   A specific geographic area, such as 'asia-southeast1' (Singapore) or 'us-west1' (Oregon). Each Region is isolated from failures in other Regions.  

4. Zone  
   An independent data center within a Region. Zones are labeled with an extra letter suffix (e.g., 'us-west1-a', 'us-west1-b', 'us-west1-c').


Global
└── Multi-Region: “asia” (Singapore + Taiwan)
    ├── Region: asia-southeast1 (Singapore)
    │   ├── Zone: asia-southeast1-a
    │   ├── Zone: asia-southeast1-b
    │   └── Zone: asia-southeast1-c
    └── Region: asia-east1 (Taiwan)
        ├── Zone: asia-east1-a
        └── Zone: asia-east1-b





2. Key Benefits

- Low Latency  
  Deploy your application close to end users.  
  - Users in Singapore hit 'asia-southeast1' zones for sub-20 ms response.  
  - U.S. West Coast users leverage 'us-west1' for speedy access.

- High Availability  
  Spread workloads across multiple zones within a Region.  
  - If 'asia-southeast1-a' fails, traffic seamlessly fails over to 'asia-southeast1-b' or '-c'.

- Disaster Recovery  
  Protect against entire Region outages by deploying a secondary copy in another Region (e.g., fail over from Singapore → US West).

- Regulatory Compliance & Data Residency  
  Keep data in-region to satisfy local data sovereignty laws (e.g., “all data must stay within Singapore”).




3. Naming Conventions

- Region: '<continent>-<direction><number>'  
  e.g.,  
  - 'us-west1' (U.S. West)  
  - 'europe-west3' (Europe, West)

- Zone: '<region>-<letter>'  
  e.g.,  
  - 'us-west1-a'  
  - 'europe-west3-b'

Removing the trailing letter from a zone name yields its parent region.



4. Current Global Footprint

- 25 Regions (e.g., 'us-central1', 'asia-south1', 'europe-north1')  
- 76 Zones across those regions  
- Additional “Coming Soon” Regions announced regularly  

Google interconnects all zones and regions with its private, high-speed fiber network—carrying over 40 % of global Internet traffic for rapid cross-region data transfer.



5. When to Leverage Each Level

- Zone-level redundancy:  
  Deploy multiple instances of a service (Compute Engine, GKE, Cloud SQL replicas) across zones in the same Region to guard against isolated data-center failures.

- Region-level failover:  
  Use global load balancing or Cloud DNS geo-routing to shift traffic to a healthy Region during a regional outage or for planned maintenance.

- Multi-Region storage:  
  For Cloud Storage, choose Multi-Regional buckets when you need automatic data replication across Regions for highest availability and lowest read latency.



With this structure in your notes, you can architect GCP workloads to meet stringent SLAs for performance, resilience, and compliance.

GCP Account Types and Provisioning:
Google Cloud lets you interact and provision resources under two identity models. Although the creation steps are the same, each model has distinct scopes, governance and use-case implications.



1. Identity Models

- Google Account  
  • A personal account tied to a Gmail or Cloud Identity email  
  • Ideal for individual experimentation, tutorials and personal projects  

- Organization Account  
  • Backed by a Google Workspace or Cloud Identity domain  
  • Provides an Organization node for centralized resource management  
  • Required for certain demos and enterprise-level governance  



2. Creation Process

1. Sign in with your chosen identity (Gmail/Cloud Identity email or Workspace domain user).  
2. Accept terms and set up billing (link a credit card or invoicing profile).  
3. For Organization accounts, Cloud Identity/Workspace admin verifies domain and is automatically granted an Organization node.  

*Regardless of identity, you gain access to the GCP Console, API access, Cloud Shell and the ability to create Projects and provision resources.*



3. Key Differences

| Aspect              | Google Account                    | Organization Account                          |
|---------------------|-----------------------------------|-----------------------------------------------|
| Resource Hierarchy  | Project → Resources               | Organization → Folder(s) → Project → Resources |
| IAM Scope           | Grants applicable within a Project| Grants can be applied at Org or Folder level  |
| Billing Management  | Project-level billing             | Centralized billing across all Org projects   |
| Policy Enforcement  | No-policy guardrails              | Org policies (e.g., allowed regions, enforce labels) |
| Demo Compatibility  | Most tutorials                    | All enterprise and organization-scoped demos  |



4. When to Use Each Account

- Choose Google Account when:  
  - You’re learning GCP concepts or running small, personal workloads  
  - You don’t need organization-wide policies, shared billing or directory integration  

- Choose Organization Account when:  
  - You require centralized IAM, resource hierarchy and policy enforcement  
  - You’re collaborating across teams under a corporate domain  
  - You need to run demos or features that explicitly require an Organization node  



5. GCP Resource Hierarchy Diagram

Organization (only with Org Account)
 ├─ Folder “Marketing”
 │    ├─ Project A
 │    └─ Project B
 ├─ Folder “Engineering”
 │    └─ Project C
 └─ Project D
Project (with either account)
 ├─ Compute Engine VM
 ├─ Cloud Storage Bucket
 └─ BigQuery Dataset


- Organization: Top-level container (exists only if you use an Organization Account).  
- Folder: Optional grouping for projects, used for delegated IAM.  
- Project: Billing unit, API enablement and identity boundary.  
- Resources: Individual services and assets you create.



With these notes, you can decide which identity model fits your needs and understand how each shapes billing, access control and resource organization in GCP.

Identity and Access Management:

2. Core functions

3. Why it matters

Networking Basics:

   - Control ingress and egress traffic at the VPC or subnet level  
   - Define allow/deny policies by IP range, port, and protocol

Identity and Access Management (IAM):
IAM governs “who can do what on which resource.” Every IAM policy combines three elements:

- Who: the identity  
- What: the action or permission (create, update, delete, etc.)  
- Which Resource: the GCP service or asset (Compute Engine, Cloud Storage, 200+ others)  

A policy binds identities to roles (collections of permissions) on specific resources.  



Core IAM Concepts:

- Roles  
  - Built-in roles: predefined for each GCP service  
  - Custom roles: created when built-in roles don’t meet requirements  
- Service Accounts  
  - Identities for non-human actors (applications, scripts)  
  - Used to authenticate and authorize API calls  



Identity Types (“Who”):

| Identity Type         | Organization Scope       | Description                                            |
|-----------------------|--------------------------|--------------------------------------------------------|
| Google Account        | No organization          | Personal Gmail or Cloud Identity; ideal for demos      |
| Google Group          | Can span Org or personal | Aggregates multiple Google Accounts into one identity  |
| Google Workspace      | Yes                      | Org-managed, includes G Suite apps (Gmail, Drive)      |
| Cloud Identity        | Yes                      | Org-managed, no G Suite apps; pure identity provider   |
| Service Account       | Yes (project/org)        | Non-human identity for apps and automation             |



Built-in vs. Custom Roles:
- Built-in roles  
  - Google-defined; cover common job functions (e.g., 'roles/storage.objectViewer')  
- Custom roles  
  - You define a set of permissions when built-in roles are too coarse or too broad  



Logging In: Google vs. Organization Account

1. Personal Google Account  
   - Sign in at 'console.cloud.google.com' (e.g., 'GCPtutorial.2020@gmail.com')  
   - No Organization node shown; project-level view  
   - Free-trial warnings may appear if billing has lapsed  

2. Cloud Identity / Workspace Account  
   - Sign in with an org email (e.g., 'admin@learncloudwith…com')  
   - Console auto-selects the associated Organization  
   - Toggle between Org-scoped and “No organization” as needed  



Why This Matters:
- Assign least-privilege access by crafting precise IAM policies  
- Group users via Google Groups for bulk role assignments  
- Use service accounts for application-to-application authentication  
- Distinguish between personal vs. organization accounts to enable Org-level governance

IAM Roles and Permissions:
Identity and Access Management (IAM) uses roles to bundle fine-grained permissions, then binds those roles to identities on specific resources. You cannot assign permissions directly—only roles.



Key Concepts:
- Permissions  
  Individual actions on resources (e.g., 'compute.disks.get', 'storage.buckets.list').  

- Roles  
  Collections of permissions. Three main categories:  
  1. Primitive roles (legacy, broad)  
  2. Predefined (service-specific) roles  
  3. Custom roles (user-defined)  

- Policy Binding  
  A policy ties an identity (Who) to a role (What) on a resource (Which).



Role Categories:
1. Primitive Roles (Legacy)  
   Broad, account-wide roles not tied to a specific service.  
   | Role   | Scope               | Approx. Permissions | Use Case / Recommendation               |
   |--------|---------------------|---------------------|------------------------------------------|
   | Owner  | All resources       | ~4,500              | Full control; legacy only, avoid if possible |
   | Editor | All resources       | ~3,000 – 4,000      | Read/write; legacy only                   |
   | Viewer | All resources       | ~1,900              | Read-only; legacy only                    |

2. Predefined Roles  
   Google-defined for each service, covering common job functions.  
   - Compute Admin ('roles/compute.admin'): ~560 VM-related permissions  
   - Storage Admin ('roles/storage.admin'): full Cloud Storage control  
   - Storage Object Admin ('roles/storage.objectAdmin'): object-level CRUD in buckets  
   - Storage Object Creator/Viewer: write-only / read-only access to objects  
   - BigQuery Roles: 14 roles (e.g., 'bigquery.dataEditor', 'bigquery.jobUser')  

3. Custom Roles  
   When predefined roles are too coarse or too broad, combine exactly the permissions you need and create a custom role at the organization or project level.



Viewing & Filtering Roles in the Cloud Console:
1. Go to IAM & Admin → Roles.  
2. Use the search bar or filter by service:  
   - Type 'compute admin' → shows Compute Admin role with 560 perms  
   - Type 'roles/owner' → shows the Owner primitive role with ~4,500 perms  
   - Type 'Cloud Storage' → lists all Storage roles (admin, objectAdmin, objectViewer, etc.)  
   - Type 'BigQuery' → lists 14 BigQuery-specific roles  



Principle of Least Privilege:
- Assign the smallest scope necessary:  
  - Favor service-specific predefined roles over primitive roles.  
  - Use custom roles for exact permission sets when needed.  
- Avoid primitive roles (Owner, Editor, Viewer) for daily operations—they grant excessive, account-wide access.  
- Group users into Google Groups and assign roles to the group for easier management.



Permissions Flow Diagram:
'''
[Identity] 
    ↳ binds to 
[Role] ── contains ──▶ {permission 1, permission 2, …}
    ↳ applies to 
[Resource]
'''

- Identities include Google Accounts, Google Groups, Workspace/Cloud Identity users, and Service Accounts.  
- Roles package permissions.  
- Resources are GCP services (Compute Engine, Cloud Storage, BigQuery, etc.).  



With these notes, you understand how IAM roles encapsulate permissions, how to explore built-in roles, and how to apply the principle of least privilege in GCP.
